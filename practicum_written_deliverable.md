# Practicum Written Deliverable: Researcher Intelligence Platform

## Project Scope and Objectives

The practicum project is building a Researcher Intelligence Platform for a sponsoring company whose work spans advanced semiconductor processes, materials science, photonics, plasma science, deposition, metrology, packaging, robotics, digital twins, and quantum computing. In each of these areas the company needs to identify academic researchers who are relevant to a specific technical need — potential collaborators, research partners, advisors, or hiring prospects. The conventional approach of searching by citation count or keyword surfaces well-known figures in a broad field, not necessarily the people doing the most relevant work for a particular question. This platform is designed to fix that.

The system has three integrated layers. The backend collects and organizes scholarly data, builds structured researcher profiles, and exposes a ranking API that accepts a plain-text query and returns a ranked, explainable list of researchers. The frontend, built by a teammate, lets users submit queries and view the results the API returns. The Gemini-powered conversational AI layer, currently in development, sits on top to make the system accessible through natural language dialogue: it interprets imprecise or misspelled queries before the API call, and after the API call it uses the structured ranking output to explain in plain language why each researcher appeared and how they compare.

The ranking model is a core contribution of the project. Rather than sorting by lifetime citation count, it combines two signals per researcher: a Q score measuring query-specific relevance (the average cosine similarity of a researcher's top-matched papers to the query, zero-padded to penalize single-paper coincidences) and an impact score — either a normalized h-index (H) for general impact or a query-aware citation sum (R) that counts only citations from papers that matched the query, optionally within a selected year window. The final score is a configurable weighted combination. This design lets the company tune results to the decision at hand: scouting emerging researchers calls for different weights than identifying senior advisors. Every response also includes score components, primary driver labels, matched papers, and contribution metrics, which is the evidence the Gemini layer uses to generate grounded explanations.

## Work Plan and Timeline

The project began in January 2026 with problem scoping and data-source research. The team defined the business objective and evaluated scholarly data sources, settling on OpenAlex as the primary source for papers, authors, institutions, and concept hierarchies, with Semantic Scholar as a fallback for missing abstracts and citation data.

System design followed in January and February. The architecture separates expensive work — crawling APIs, computing career metrics, generating embeddings — into an offline pipeline that runs on a recurring schedule, keeping the online ranking API fast and cost-efficient at query time. The database schema was designed to cover researchers, institutions, papers, topics, and collaboration relationships, with paper abstract embeddings stored separately in Pinecone for semantic retrieval.

Pipeline construction and API development ran from February through spring. The four pipeline stages — paper discovery from OpenAlex, author extraction and deduplication, profile and institution enrichment, and final assembly into MySQL and Pinecone — were implemented and validated. Domain and topic mapping happened in parallel: translating the sponsor's technical areas into OpenAlex-compatible topic identifiers required generating 132 topic candidates, organizing them into category summaries, and running overlap analysis to avoid coverage gaps. This work was foundational to retrieval quality.

The ranking API scoring model was refined in May 2026, particularly around fallback weight configuration and handling researchers with sparse paper coverage. The functional and technical design documents were finalized on May 7, 2026. A validated end-to-end test export confirmed that retrieval expansion, scoring, and explainability all function together, surfacing 1,989 unique researchers across 2,000 Pinecone matches over three expansion rounds. The frontend, built concurrently by a teammate, is now integrated with the backend. The Gemini conversational layer is the active current development focus.

## Key Project Findings and Deliverables

The most important finding is that relevance and impact are independent signals that need to be separated and tunable. A researcher with deep topical focus may have a modest h-index; a broadly distinguished senior researcher may rank lower on a narrow query. Combining these signals explicitly — and letting the company adjust the weights — produces more useful rankings than either dimension alone. The iterative retrieval expansion design was validated empirically: a naively shallow Pinecone query would miss a large fraction of the candidate pool, and the expansion mechanism broadened results significantly while keeping query costs bounded. Domain coverage was found to be foundational rather than optional: if a sponsor-relevant topic is not represented in the ingestion pipeline, those researchers cannot be surfaced regardless of ranking quality.

Explainability emerged as essential for making rankings actionable. When a result includes the supporting papers, score breakdown, and a labeled primary driver, a stakeholder can immediately assess whether it makes sense and discount coincidental matches. This structure is also what makes the Gemini layer possible without hallucination risk — the model explains the evidence already present in the response rather than inventing reasons.

Completed and in-progress deliverables include the offline researcher data pipeline, the online FastAPI ranking service with configurable Q/H/R scoring, iterative retrieval expansion, depth enrichment, Pareto filtering, and full explainability output; MySQL schema and upsert support; Pinecone integration; Docker and Cloud Run deployment assets; functional and technical design documents; topic mapping artifacts and overlap analysis across 132 candidates; a validated ranking results workbook; the teammate-built frontend; and the Gemini conversational layer in active development.

## Benefits to the Sponsoring Company

The platform gives the company a faster and more consistent way to find academic experts across all of its technical areas. Instead of manual search across disconnected databases, a user submits a query and receives a ranked list with supporting evidence in seconds. The Gemini layer lowers the barrier further: users can describe a need informally or with imprecise terminology, and the system handles interpretation, spelling correction, and query normalization before searching. After results are returned, Gemini explains the rankings in plain language, making the output useful to business development, product, and leadership stakeholders who do not need to understand cosine similarity or h-indices.

The configurable ranking model means the same platform serves different decision contexts. The architecture is also built to grow: the pipeline can ingest new domains, the scoring model can evolve without changing the API interface, and the Gemini layer can be extended to multi-turn dialogue, comparison queries, and follow-up refinement as the product matures.

## Next Steps the Team is Proposing for Ongoing Project Success

The immediate priority is completing and integrating the Gemini conversational layer. This includes query interpretation and correction before the API call, post-ranking natural language explanation generation, and front-end integration so users experience a seamless dialogue rather than switching between an input form and a raw results list.

On the data side, the team proposes expanding topic coverage for the remaining sponsor domains where OpenAlex concept alignment is incomplete, and running a full knowledge base consistency audit to reconcile database records, vector index contents, and exported artifacts. Scheduled pipeline refresh runs should be operationalized so the knowledge base stays current without manual intervention.

For ranking quality, the team proposes structured evaluation across a broader set of query categories using known ground-truth researchers as benchmarks, and collecting early user feedback from internal stakeholders to calibrate the default Q and H/R weights toward the company's most common use cases.

Longer-term, the team recommends adding monitoring and observability dashboards for the ranking service, implementing a ranking feedback loop so user interactions can improve results over time, and exploring extension of the platform to adjacent domains beyond the current semiconductor and advanced technology focus.
